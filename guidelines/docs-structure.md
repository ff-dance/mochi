# 文档结构与规格流程

> 唯一来源：`docs/` 的目录、命名、流程与模板规则。`CLAUDE.md` 只放速查。

## 目录

| 位置 | 内容 |
|---|---|
| `docs/product-specs/<domain>/` | 产品规格：用户目标、业务规则、流程、验收标准 |
| `docs/design-specs/<domain>/` | 设计规格：技术方案（分层、模型、状态、Service 接口） |
| `docs/tasks/<domain>/` | 实施任务：由设计规格拆出的可执行任务与执行记录 |
| `docs/templates/` | 三类文档的模板 |
| `docs/decisions.md` | 项目级已确认决策与待验证项；与规格冲突时以它为准 |

`<domain>` 为功能领域，小写 kebab-case（如 `player`、`library`），出现第一个功能时再建目录，不预建空目录。

## 流程

```text
product-spec → design-spec → tasks → 实现 + 测试
```

- 同一功能的三份文档共用编号：`<domain>/NNN-<slug>.md`（`NNN` 为领域内 3 位递增序号，`slug` 为 ASCII kebab-case）。
- 设计规格顶部链接对应的产品规格；任务文件顶部链接对应的设计规格。
- 每条验收标准（AC）使用唯一编号（`AC-1`…），写明前置、用户动作和可观察结果；产品规格不规定实现细节。
- 任务以可验证目标为单位（见 `core.md` §4），每个任务写明验证方式，完成后勾选并记录结果。
- 已有文档优先原位更新，不另起新文件。

## 事实优先级

文档与代码冲突时：代码与测试为当前事实，产品规格为目标事实。发现冲突先向用户指出，再决定改代码还是改文档。

## 过程产物

原型、验证脚本、截图、运行报告等过程产物放本地 `artifacts/`（已 gitignore，不入库，克隆后不存在），不入 `docs/`；长期有效的结论整理成正式文档后再放入 `docs/`。
