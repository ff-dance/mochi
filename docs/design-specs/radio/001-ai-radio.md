# AI 音乐电台 · 技术方案 v0.1

- 领域：`radio`　编号：`001`
- 产品规格：[AI 音乐电台](../../product-specs/radio/001-ai-radio.md)

> 导出自 Claude Doc「AI 音乐电台 · 技术方案 v0.1」（rev 16，日期 2026-10-08）。三张图（总体架构、单曲生命周期、实施路线图）在这里改写成了文字。与 [decisions.md](../../decisions.md) 冲突时以 decisions.md 为准。

用 Swift 写一个原生 macOS 菜单栏 App，在本地编排「选曲 → 取资料 → 写口播 → 合成语音 → 混音播放」整条流水线；大模型与 TTS 走你自配的云端，口播在上一首播放期间预生成，保证歌曲之间无缝衔接。

## 关键决策

选型遵循两条：能用系统原生能力的不引入第三方，能让你自行配置的不写死。目标系统为 macOS 15 及以上。

| 层 | 选择 | 理由与备注 |
| --- | --- | --- |
| 语言与界面 | Swift + SwiftUI，窗口层用 AppKit | 悬浮岛需要 AppKit 的 NSPanel，内容用 SwiftUI 画 |
| 运行形态 | 菜单栏 App，无 Dock 图标 | 常驻后台，随时唤起 |
| Apple Music | MusicKit for Swift | 官方接口，可读最近播放与收藏；压低音量的做法待验证 |
| QQ 音乐 | 本地 Python 小服务，封装非官方的 qqmusic-api-python | 复用现成库，不用 Swift 重写逆向接口；App 通过 localhost 调用，也可直接换成社区 MCP server |
| 播放与混音 | AVAudioEngine | 对取得播放链接的音源，淡入淡出与 ducking 完全可控 |
| 大模型 | 云端，由你自配，默认 GLM-5.3-Flash | 抽象成 LLMProvider，换模型只改配置 |
| TTS | 云端，由你自配，温柔女声 | 抽象成 TTSProvider，口播脚本与语音分开 |
| 天气 | WeatherKit 或免费的开放天气接口 | WeatherKit 需要开发者账号，开放接口作备选 |
| 本地存储 | SwiftData | 数据量很小，只存偏好、短期历史与口播缓存 |
| 密钥 | macOS 钥匙串 | 模型密钥与 QQ 音乐登录凭证不明文落盘 |

## 总体架构

（原图的文字版）分三层：

- **界面层**：刘海悬浮岛（NSPanel + SwiftUI）、菜单栏面板（MenuBarExtra）、设置页。只负责显示和接收指令（跳过、喜欢、暂停等）。
- **本地核心编排**：情境采集 → 推荐引擎 → 口播生成（取资料 → 写脚本 → 合成语音）→ 播放与混音；统一的 `Player` 接口；SwiftData 存储。
- **外部服务**（都隔着接口）：音源（Apple Music / MusicKit，QQ 音乐 / 本地 Python 服务）、云端大模型（LLMProvider）、云端 TTS（TTSProvider）、天气、资料来源（MusicBrainz、维基百科）。

界面层只负责显示和接收指令；核心编排把四步串成一条流水线，其中口播生成是产品的特色，也是对延迟最敏感的一步。云端服务、音源和存储都隔着接口，换模型或换音源时不用改编排。

## 单曲生命周期

（原图的文字版）两条并行轨道：

- **预生成轨道**（歌曲 N 一开始播放就触发）：为 N+1 选曲 → 取资料 → 写脚本并校验 → 合成语音 → 口播音频与字幕写入缓存、标记可播放；同时把 N+1 下载到临时文件。
- **播放轨道**：N+1 开始播放时，口播音频已在缓存中，与歌曲同时开始；音乐压低为背景，口播结束后渐强；歌曲结束后清理该首的口播缓存与临时文件，并触发 N+2 的预生成。

歌曲 N 一开始播放，就触发下一首的预生成；等 N+1 开始播放时，口播音频已经在缓存里，直接叠放在歌曲开头，音乐压低为背景。取资料或合成失败时不阻塞播放，降级方案见「异常与降级」。

## 推荐引擎

推荐引擎不做排序，而是在情境约束下做加权随机抽样：先按配比抽出「熟悉 / 相邻 / 意外」三档之一，再在该档内按情境得分抽歌。选歌全由程序完成，不交给大模型，结果稳定、便宜、可调试。

1. **候选池**：熟悉档来自本地偏好库（最近播放、收藏、重复播放）；相邻档优先用音源自带的相似艺人或相关推荐，没有则按风格标签搜索；意外档从与近期偏好距离较远的风格里随机搜索。
2. **情境打分**：把天气与时段映射成目标气质，给候选加分或减分，映射表放在配置里，可随时调整。
3. **多样性与冷却**：同艺人和同曲目设冷却窗口（默认同艺人 10 首内不重复、同曲 7 天内不重复，可调）。
4. **抽样**：按配比（默认 30 / 50 / 20）抽档，再在档内按得分加权随机。
5. **记录理由**：把入选档位、命中的情境和关联的近期偏好写进 `Pick`，交给口播生成使用。
6. **反馈更新**：喜欢和听完加权重，跳过减权重，「不想听这类」重减；旧数据按时间衰减，保证偏好始终是「最近」的。

| 情境 | 偏向（示例，可调） |
| --- | --- |
| 雨天 | 舒缓、原声、低能量 |
| 晴朗的上午 | 轻快、中高能量 |
| 深夜 | 安静、器乐、慢节奏 |
| 周末午后 | 放松、不赶时间的曲风 |

```swift
struct Pick {
    let track: TrackRef          // 音源无关的曲目引用
    let tier: Tier               // .familiar / .adjacent / .surprise
    let reasons: [Reason]        // 命中的情境与关联偏好，供口播使用
}
```

## 口播生成

口播的真实性靠「先取资料、再写稿」保证：大模型只许使用检索到的资料写故事，资料不够时宁可不讲故事，也不凭记忆编。生成分三步：取资料、写脚本、合成语音。

**1. 取资料。** 用曲名与艺人去查 MusicBrainz、维基百科和音源自带的专辑信息，每条资料切成带编号、带来源的短片段。检索只发送曲名与艺人，不带位置与听歌历史。

**2. 写脚本。** 一次大模型调用，输入由下面几部分拼成：

| 输入 | 内容 |
| --- | --- |
| 人设 | Lyra 的身份、温柔而沉稳的语气、科幻管家的措辞边界、对用户的称呼 |
| 曲目 | 歌名、艺人、专辑、年份 |
| 资料片段 | 带编号与来源，是故事唯一可用的事实 |
| 情境 | 天气、时段，以及 `Pick` 里记录的推荐理由 |
| 约束 | 目标 60–120 字、句子短、结尾自然引出歌曲 |
| 上下文 | 前几段口播的摘要，避免开场白和句式重复 |

模型按固定格式输出，程序再校验：

```json
{
  "mode": "story",
  "script": "……",
  "facts_used": [2, 5]
}
```

- `mode` 为 `story` 或 `reason_only`；资料为空或不可靠时只能是 `reason_only`，内容限于推荐理由与情境。
- 校验 `facts_used` 全部存在于资料片段中；脚本超长或校验不通过时重试一次，仍失败则降级为 `reason_only`。
- 字数上限按语速折算成秒数，把口播控制在 30 秒以内，避免音乐被压低太久。

**3. 合成语音。** 脚本交给 TTS 生成音频。TTS 若返回时间戳，字幕按时间戳对齐；没有就按字数估算。音频与字幕一起写入缓存，标记为可播放。

## 播放与混音

两类音源的混音能力不同：能拿到播放链接的音源可以完全自己控制音量，Apple Music 受 DRM 限制，压低音乐的方式还要验证。口播与歌曲同时开始，音乐先压低、口播结束后渐强，不去分析前奏。

**能取到播放链接的音源（QQ 音乐，路径 B）**

- 播放前先把下一首下载到临时文件，用 AVAudioEngine 播放：一个节点放音乐，一个节点放口播，两路各自控制音量。
- ducking 是对音乐节点的音量做渐变：口播开始时压到约 20%，口播结束后渐强回原音量，渐变时长约半秒，两个数值都可调。
- 预先下载还有两个好处：网络抖动不会打断播放，淡入淡出可以精确对齐。

**Apple Music**

歌曲受 DRM 保护，不能走自己的音频引擎，只能让 MusicKit 播放器自己播。压低音乐有四种做法，按顺序验证：

| 做法 | 说明 | 状态 |
| --- | --- | --- |
| 调播放器自身音量 | 若 MusicKit 播放器提供可用的音量接口，直接对它渐变 | 待验证 |
| 控制 Music.app 的音量 | 用 AppleScript 调整 Music.app 的播放音量，仅适用于由 Music.app 播放时 | 待验证 |
| 调系统输出音量 | 口播也会一起变小，需要对口播做增益补偿，效果最差 | 备选 |
| 先口播后放歌 | 不叠放，歌曲之间插入口播，放弃「口播叠在前奏上」的效果 | 兜底，必定可行 |

**其他**

- 媒体键与「正在播放」信息用 MPRemoteCommandCenter 和 MPNowPlayingInfoCenter 接入。
- 监听系统睡眠与唤醒，唤醒后恢复播放并重新检查预生成缓存。
- 播放器对上层只暴露统一的 `Player` 接口（播放、暂停、跳过、设置音乐音量），上层不关心当前是哪类音源。

## 界面：刘海悬浮岛与菜单栏

macOS 没有系统级的灵动岛，所以悬浮岛是一块自绘的无边框面板，贴在屏幕顶部正中，从刘海处展开；菜单栏面板作为常驻入口和兜底。

**窗口实现**

- 用 AppKit 的 NSPanel：无边框、背景透明、不抢焦点（nonactivatingPanel），窗口层级高于菜单栏，加入所有桌面空间。
- 判断是否有刘海：看 `NSScreen.safeAreaInsets.top` 是否大于 0；刘海宽度 = 屏幕宽度减去 `auxiliaryTopLeftArea` 与 `auxiliaryTopRightArea` 的宽度。
- 面板顶边对齐屏幕顶边、水平居中，内容用 SwiftUI 绘制，展开与收起用动画过渡。
- 没有刘海的屏幕（外接显示器等）降级为顶部居中的胶囊，尺寸与动画相同。

**三种状态**

| 状态 | 触发 | 显示 |
| --- | --- | --- |
| 收起 | 默认，音乐播放中 | 刘海两侧各露出一小块：左边封面缩略，右边声波 |
| 口播 | 口播开始，结束后回到收起 | 向下展开，显示 Lyra 的实时字幕与声波 |
| 悬停展开 | 鼠标移到刘海区域 | 歌名、艺人，喜欢、跳过、暂停按钮 |

**菜单栏面板**

- 用 SwiftUI 的 MenuBarExtra（窗口样式）做常驻图标，下拉显示当前曲目、历史记录入口与设置入口。
- 历史记录的「阅后即焚」在这里实现：面板关闭时清除已查看的条目，后台定时清除超过 24 小时的未查看条目。

**待验证**

- 其他应用全屏时，悬浮岛能否仍显示在刘海区域。
- 多显示器下的跟随策略：暂定固定在带刘海的内置屏。

## 数据与配置

所有数据都留在本机，只有四张表，外加设置和密钥。播放过的口播音频与临时音乐文件在歌曲结束后删除，不堆积。

| 数据 | 主要字段 | 用途与保留 |
| --- | --- | --- |
| Track | 音源、音源内 ID、歌名、艺人、专辑 | 音源无关的曲目引用，跨音源匹配用 |
| PlayEvent | 曲目、开始时间、听完比例、动作（喜欢、跳过、屏蔽） | 反馈信号与短期历史；历史条目阅后即焚，最长保留 24 小时，反馈信号折算进 Preference 后删除 |
| Preference | 艺人或风格标签、权重、更新时间 | 近期偏好，权重随时间衰减 |
| Voiceover | 曲目、脚本、使用的资料编号、模式、音频路径、字幕 | 预生成的口播缓存，播放后删除 |

**设置**（用 UserDefaults）：口播频率、三档配比、冷却窗口、音乐压低的音量与渐变时长、屏蔽艺人与曲风、勿扰时段、主理人对用户的称呼。

**模型配置**

- 大模型与 TTS 各自抽象成一个接口（`LLMProvider`、`TTSProvider`），配置项是接口地址、模型名、超时与重试次数；密钥放钥匙串。
- 默认预填 GLM-5.3-Flash，模型 ID 为 `glm-5.3-flash`，接口地址与调用方式以智谱 [BigModel 文档](https://docs.bigmodel.cn/api-reference/模型-api/对话补全) 为准。该模型的思考模式不能关闭，但可以用 `reasoning_effort`（low / high / max）调强度，口播这类短文本先试 low 以缩短首字延迟；解析返回结果时只取最终回答，忽略推理内容。
- TTS 的接口把「文本 + 音色」换成「音频 + 可选时间戳」，具体服务由你选定后再接入。
- 设置页提供「测试连接」按钮：各发一次最小请求，确认地址、密钥与模型名都可用。

**密钥与凭证**

- 模型密钥与 QQ 音乐的登录凭证都放在 macOS 钥匙串，不写进配置文件、日志或口播缓存。
- 日志默认不记录脚本全文与听歌记录，只记录耗时与错误码。

## 异常与降级

总原则：口播是锦上添花，任何一环失败都不能让音乐停下来。失败时逐级降级，最差的结果是只放歌、不口播。

| 环节 | 失败情形 | 处理 |
| --- | --- | --- |
| 取资料 | 超时或没有可靠资料 | 脚本模式改为 `reason_only`，只讲推荐理由与情境 |
| 写脚本 | 超时、限流、格式或事实校验不通过 | 重试一次；仍失败则用本地预置的短模板口播，再不行就跳过口播 |
| 合成语音 | 超时或服务报错 | 重试一次；仍失败则跳过口播，直接放歌 |
| 预生成来不及 | 歌曲 N 结束时口播还没准备好 | 等一个短的宽限期（默认 3 秒，可调），仍未就绪就放弃这段口播，直接放 N+1 |
| 找不到歌或下载失败 | 无版权、链接失效、下载中断 | 在同一档内重新抽一首候选 |
| QQ 音乐接口失效 | 非官方接口变更，或登录凭证过期 | 标记该音源不可用，推荐暂时只用 Apple Music，并在设置页提示重新登录 |
| 网络断开 | 预生成无法继续 | 播完已缓存的下一首及其口播，随后提示离线，不再生成新口播 |
| 连续快速跳过 | 用户快速切歌 | 取消进行中的预生成，丢弃被跳过歌曲的口播，为新的下一首重新开始 |
| 系统睡眠与唤醒 | 唤醒后缓存可能已过期 | 重新检查缓存，必要时重新预生成 |

## 实施路线图

（原图的文字版）4 个阶段、3 个关口：

阶段 0 验证 → **关口 0**（压低音乐的做法已定、口播耗时可接受）→ 阶段 1 核心闭环（选曲 + 口播 + 混音，自用迭代）→ **关口 1** → 阶段 2 悬浮岛与菜单栏体验打磨、历史阅后即焚 → **关口 2** → 阶段 3 QQ 音乐等更多音源、个性化与记忆能力。

阶段 0 先把最不确定的两件事验证清楚：压低音乐的做法，以及 QQ 音乐能否稳定取链接播放。验证的具体清单见[产品规格](../../product-specs/radio/001-ai-radio.md) 第 13 节（与本地 `artifacts/stage0/README.md`）；不过关口 0，不进入阶段 1。
